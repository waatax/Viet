# Viet 全站介面與通勤聽力盤點

日期：2026-11-12（台北）。基線：本機 commit `30e6bf91`、package 2.24.0。

本輪依需求「先檢查 Repository，完成分析報告，等我確認後再開始修改」執行盤點。未修改應用程式、未產生新語音、未提交或部署。測試產生既有快取與 dist 建置輸出；它們不是功能修改。

**使用者補充：至少越文＋中文才算可學習。預設全部播放必須採「越文 → 中文」；純越文僅是選用模式，不能作為第一階段交付替代。**

## A. 架構與部署

- React 18；本機建置實際 Vite 5.4.21。以 `App.jsx` 的 hashchange、activeTab 與條件掛載實作路由，未使用 react-router。
- `vite.config.js` 的 base 是 `/Viet/`；主站與 `quest/index.html` 為兩個建置入口。不同 HTML 文件的導航，不等同於同一應用內 hash 路由切換。
- 模組以 lazy loading 載入，詞庫、音訊 manifest、情境資料另拆 chunk。
- `.github/workflows/deploy.yml` 在 main/master push 或手動觸發後執行測試、建置、上傳 dist，再用 GitHub Actions Pages 部署並驗證 release.json。
- `npm run deploy` 的腳本實際是檢查分支與乾淨工作目錄後 push；不是直接覆寫 gh-pages 分支。
- 本輪沒有推送；正式站最新部署版本未完成核對。網頁讀取工具無法讀取正式首頁，不據此推論網站故障。

### 根因與可沿用的實作

1. `audioEngine.js` 已有單一 media element、session 防競態、預錄 MP3、預載、Cache Storage 整合、vi-VN／zh-TW Web Speech 回退，以及失敗後線上串流回退。沿用，不另造播放器。
2. `dialoguePlayback.js` 已有逐句越中／純越、上一句／下一句、循環、跟讀停頓、媒體控制、隱藏頁面避開一般間隔 timer、錯誤暫停與 watchdog。
3. `useDialoguePlayback.js` 為每個使用它的元件建立 sequencer，卸載 destroy，教材 signature 改變 stop。這是跨頁中斷的直接原因。
4. `WordBrowser.jsx` 與 `PhrasesModule.jsx` 各有自己的 timer／播放索引，不是共用佇列。需適配現有引擎，保留「中→越」「越中×3」等能力。
5. 現有 repeat 是重複越文後才讀一次中文，與需求的「整個越中組合重複」不同，必須明確區分，避免改壞既有跟讀訓練。
6. 現有速度是 0.6、0.75、1、1.2；沒有 1.25。沒有通勤睡眠計時、全域播放位置恢復、固定 1/2/3 秒停頓、完整例句模式與通勤隨機佇列。
7. `DialoguePlaybackBar` 的 dock 依然屬於頁內元件，portal 到 body 不會改變生命週期。它只顯示當前越文／來源，需補中文。按鈕存在 36px/42px 尺寸，不符要求的 48px。
8. `public/sw.js` 已註冊，與 offlineAudioService 共用 `viet-audio-offline-v1`。不要建立第二個快取。SW 現有 fetch handler 只處理音訊，沒有真正快取 app shell；不能宣稱斷網冷啟動可用。
9. offlineAudioService 有去重、併發限制、失敗重試、音訊 MIME 檢查、進度與缺 manifest 偵測。仍缺按模式計算、容量估計／配額提示與完整清單入口。SW 的寫入規則也要與服務的音訊驗證對齊。

高頻中文依 WordBrowser 真正朗讀的轉換（取前兩個 ` / ` 義項並用逗號連接）計算；不能只用原資料的 zh 欄位。高頻詞也必須用 vocabularyQuality 校對後資料，不能用原始 10k 的佔位例句估計錄音量。

- 既有會話抽取器盤點 287 組、2161 行，1917 個不重複中文文本；中越音檔解析／檔案檢查無失敗。
- 越文 manifest：32,764 個文字鍵 → 13,281 個不同檔案，約 209.69 MiB。
- 中文 manifest：7,146 個文字鍵／檔案，約 120.11 MiB。
- 兩份 manifest 引用的本機檔案缺失為 0。上述約 329.80 MiB 不代表包含其他整段合輯、圖片及所有公共資產的完整網站大小。
- 第一階段漢越字根＋複合詞缺 198 筆中文映射，去重為 **194 段中文文本**。若保持原解釋文字，預計新增 194 個中文 MP3；按現有中文檔案平均 17.21 KiB 粗估約 **3.26 MiB**，先預留 3–5 MiB。實際以錄製後位元率與時長為準。
- 第一階段這批教材無須新增越文音檔。元件內商務／音韻延伸教材應另外建立精確雙語清單後核算，194 不代表全漢越頁所有子模式的缺漏總數。
- Top 5k 有 7 筆「目前 UI 轉換後中文」未命中，應先對齊既有音檔與朗讀文字，未必需要重錄。後半 5k 則有 4925 個詞條越文未命中、4866 個中文未命中，不適合直接整庫生成；先校對與去重再報確切音檔數。
- 後半 5k 若逐條補足詞＋中文，未去重的粗上界約 9791 檔、約 160 MiB（依目前語種平均大小估算，不含例句）；這不是本次第一階段必要工作，也不是生成授權。

既有 `generate_dialogue_audio.py` 可重用，使用 edge_tts、vi-VN-HoaiMyNeural／zh-TW-HsiaoChenNeural。本輪未呼叫語音供應服務。程式中的 voice 名稱不能證明商用或大量生成授權；正式生成前需核實當時服務條款、可用性與費用。沒有付費服務報價或已確認的授權結論。先只處理必要的 194 段，避免 repository 膨脹。口音需以音檔來源及聽審確認，不能以設定切換或文字變形宣稱不同口音。

## E. 視覺品牌與最小修改方案

以下為根據程式與 CSS 的改善提案；尚未做瀏覽器視覺驗收。

- 保留既有品牌色與 light/dark/sepia 主題，收斂主色、強調色與狀態色的用途。現有 index.css 多段覆寫與大量頁內 style，先整理共用 token，再分頁替換，避免一次大幅重寫樣式。
- 漢越頁首屏順序改為：簡短標題 → 搜尋／篩選 → 明顯「全部播放・越文→中文」 → 詞列。音韻長說明與進階設定可展開，讓聆聽入口先出現。
- 字根選取仍用於詳情；另給獨立發音與「從此續播」入口，避免破壞選字和組詞遊戲。
- 迷你列顯示越文、中文、進度，主要只放上一句／播放暫停／下一句。48×48px 觸控區、至少 8px 間距，語速與模式放第二列或展開面板。
- 漢越頁有 `minmax(320px, 1fr)` 的 inline grid，窄手機扣除內邊距後可能溢出；改為可收縮單欄並做實際測量。
- 頁尾預留迷你列與底部導覽的總高度，包含 safe area；驗證最後一筆教材可完整捲入視窗。

推薦方案：在 App 路由內容外掛載一個播放 session，由原 DialogueSequencer 驅動。各頁只提交教材快照並訂閱播放狀態，切換瀏覽頁不能覆寫正在播放的清單。現有小播放器提升為全站共用元件；不要建立第二個 HTMLAudioElement 播放系統。

替代方案：先僅在漢越頁接上現有 hook，修改更少，但會在第二階段再搬移生命週期，且第一階段仍無法跨頁。推薦第一階段就建立薄 session 層，先只接漢越；第二階段逐頁整合，減少重工。

## G. 執行順序與可驗收交付

1. **Phase 1 漢越雙語播放與首屏簡化**：先補必要中文預錄音檔，接入原引擎及薄 session；單項越中、全部越中、選定項目續播、空清單與快按防競態。驗收 74 字根／295 複合詞的中文不能漏讀；沒有例句時跳過例句段。
2. **Phase 2 全站整合與品牌整理**：會話、單字、短句逐頁接共用佇列，常駐迷你列，跨 hash 路由不中斷；測驗取得音訊優先權時明確暫停通勤序列。驗收手機尺寸、鍵盤焦點、中文顯示與底部留白。
3. **Phase 3 通勤設定**：保留原模式並加例句模式、1.25×、整個組合重複、固定停頓、單項／清單循環、隨機、絕對到期睡眠時間、按使用者操作才恢復上次聆聽。儲存只記必要 ID 與版本，處理損壞／不可用情況。
4. **Phase 4 音訊可靠性**：對齊文字映射、預載窗口、錯誤提示及 Media Session；做真機鎖屏、耳機與打斷恢復。若逐句鎖屏受裝置限制，評估重用既有合輯音訊作替代，不能宣稱 Web Speech 等同可靠鎖屏方案。
5. **Phase 5 離線**：沿用同一 cache，按播放模式估容量／顯示進度與失敗，補 app shell 策略與容量提示，實測斷網連播和冷啟動，明確區分瀏覽器儲存與 MP3 檔案下載。
6. **Phase 6 回歸發布**：逐項填 A01–A16 的方法、環境、結果、問題與限制；相關測試與 build 通過後，各階段建立清楚 commit，再走既有 Actions Pages 流程，核對 release revision。真機不可用的項目維持待驗收。

依原需求，盤點報告完成後等待使用者確認實作範圍。建議確認範圍為上述六階段，其中第一階段明確以「越文＋中文」為最低交付標準。
